### 一、本周工作

#### 1. 网络探测器（NetworkProbe）— 4.2 模块 ✅ 基本完成

本周重点推进了网络探测模块的开发，目前主体功能已基本落地：

- **后台探测线程**：实现独立的 daemon 探测线程，周期性地对 decode 节点执行 socket 级连通探测，可稳定获取实时 RTT 和带宽估计值

- **EWMA 预测机制**：用指数加权移动平均对带宽和 RTT 做平滑预测，避免被瞬时抖动带偏决策方向。

  > 举例：假设当前带宽以 90 Mbps → 85 Mbps → 70 Mbps → 50 Mbps 连续下降。瞬时带宽在 50 Mbps 时会直接触发 POOR 状态，但 EWMA（α=0.3）的演进是：90 → 88.5 → 82.9 → 73.1，比实际值降得更慢更平滑。这确保系统不会因为一次突发降速就过度反应、把所有 token 全降到最低精度；反过来，如果带宽忽然回升到 90 Mbps，EWMA 也不会瞬间跳上去，而是平缓爬升，避免策略来回震荡。
  
  > 反之在带宽稳定时，EWMA 会收敛到接近实际值，给精度分配器一个靠谱的预算基础。

- **三级网络状态判定**：用双阈值滞后的方式将网络划分为 GOOD / DEGRADED / POOR 三个等级，决策更稳健。

  > 判定逻辑：
  > | 条件 | 状态 | 含义 |
  > |------|------|------|
  > | 带宽 ≥ 50 MB/s **且** RTT ≤ 5 ms | GOOD | 带宽充足，可以传高精度 |
  > | 带宽介于 10~50 MB/s **或** RTT 处于 5~50 ms | DEGRADED | 网络有压力，需要选择性降级 |
  > | 带宽 ≤ 10 MB/s **或** RTT ≥ 50 ms | POOR | 带宽严重不足，所有 entry 走最低精度 |
  >
  > 关键细节是"滞回"设计——从 GOOD 降到 DEGRADED 和从 DEGRADED 恢复到 GOOD 使用的是同一组固定阈值，但实际实现中还可以加入回差（hysteresis），比如从 DEGRADED 回升到 GOOD 需要带宽超过 60 MB/s 而不是 50，防止在边界来回跳动。

- **校准机制**：实现 `calibrate_with_transfer()` 接口，利用首次实际 KV Cache 传输的真实数据来初始化带宽估计。

  > 纯探测包只有几十字节，跟实际传输几 MB 的 KV Cache chunk 完全是两回事——用探测包测出来的带宽往往虚高。校准机制的做法是：第一次传输完成后，用 `实际传输数据量 / 实际耗时` 算出一个真实带宽，用它初始化 EWMA。后续的探测在此基础上增量更新，而不是从冷启动猜测。
  >
  > 举个例子：探测包测出 200 Mbps，但第一次传了一个 10 MB 的 tensor 用了 1.5 秒，实际带宽约 53 Mbps。校准后 EWMA 就从 53 Mbps 开始，后续再结合周期性探测做微调。这样精度分配器拿到的预算不会离谱。

- **接口定义**：输出 `NetworkSnapshot` 数据结构，下游模块可直接消费。

  ```python
  @dataclass
  class NetworkSnapshot:
      timestamp: float          # 时间戳
      bandwidth_bps: float      # 当前带宽 (bytes/sec)
      bandwidth_ewma: float     # EWMA 预测带宽——精度分配器用的就是这个
      rtt_ms: float             # 当前 RTT
      rtt_ewma: float           # EWMA 预测 RTT
      state: NetworkState       # GOOD / DEGRADED / POOR
      budget_bytes: float       # 预算 = bandwidth_ewma × max_delay（当前默认 0.5s）
  ```

  > 下游模块（PrecisionAllocator）拿到的核心字段是 `budget_bytes`——它表示在当前网络条件下，系统愿意花多少数据传输量来完成一轮 KV Cache 传输。

> 目前基础功能已基本成型，后续还需要在 x86 + Jetson 异构链路上做一轮实际环境验证，以及 EWMA 参数 α 的进一步调优。

#### 2. 精度分配器（PrecisionAllocator）— 4.3 模块 🔄 正在推进中

本周启动精度分配模块的开发，目前核心逻辑正在落地中。

##### 整体设计思想

KV Cache 本质上是一堆张量，按照 `(layer, token_position)` 组织成一个二维网格。我们这个方案的出发点是：**同一个 KV Cache 里，不同位置的内容对最终生成质量的影响是不一样的，所以不应该用统一的精度去传输它们。**

这就引出了一个资源分配问题：
- **资源**：有限的带宽预算（从 NetworkProbe 拿到的 `budget_bytes`）
- **分配对象**：KV Cache 中每个 `(layer, token)` 位置的张量（我们把每一个这样的位置叫做一个 **entry**，可以理解为 KV Cache 这个二维表里的一个单元格）
- **目标**：在预算不超的前提下，让"重要"的 entry 用高精度传，"不重要"的 entry 用低精度传，整体达到最好的生成质量

##### PIA 贪心算法是如何工作的

**核心思路很简单**：假设数据总共有 10000 个 entry，先全都给最差的精度（INT2，省带宽），省下来的带宽预算，按"谁更重要就先给谁升级"的原则从高到低分配。

具体步骤：
1. 先算一下全部用 INT2 需要多少带宽，剩下的预算有多少
2. 把所有 entry 按重要性评分从高到低排个队
3. 从最重要的 entry 开始，挨个问："给你升一级到 INT4，当前剩余的预算够不够？"
   - 够 → 升级，扣掉升级成本，看下一个 entry
   - 不够 → 跳过，看下一个（更不重要的 entry 就更没机会了）
4. 全部过完后，升级过的 entry 走 INT4，剩下的走 INT2；如果预算还有得多，继续尝试往 FP8、FP16 升级

这里的"升级成本"就是升一级多消耗的字节数：INT2 → INT4 多花 0.25 bytes/element，INT4 → FP8 多花 0.5 bytes，FP8 → FP16 多花 1 byte。

**这个策略能保证**：在预算约束下，最重要的那些 token 分到最高精度，不重要的 token 用低精度凑合，整体传输质量（加权的 accuracy）是当前条件下最优的。

##### 重要性评估（由上游 4.1 模块提供）

每个 entry 的重要性评分 `I(l, t)` 融合了三个维度的信息，最终是一个 0~1 之间的分数：

```
I(l,t) = 0.6 × AttentionScore(t) + 0.25 × LayerSensitivity(l) + 0.15 × PositionDecay(t)
```

- **AttentionScore(t)**：token t 在 attention 计算中被其他 token "关注"的程度。关注度越高，说明这个 token 对后续生成越关键
- **LayerSensitivity(l)**：第 l 层对量化的敏感度。有些层数值分布比较均匀，量化了也不太影响精度；有些层数值分布很集中，量化的误差就大。这个系数通过每层张量的变异系数（CV）来估计
- **PositionDecay(t)**：位置衰减。直觉上，离生成位置越近的 token 越重要，越远的可能已经被"遗忘"了，所以权重更低

三个维度的权重（0.6、0.25、0.15）当前是经验值，后续会通过消融实验来标定。

##### 当前落地情况

- `PrecisionAllocator` 的基本框架已经搭好，FP16 / FP8 / INT4 / INT2 四级精度的配置体系和参数标定表已完成
- PIA 贪心算法的核心流程已编写完成：entry 收集 → 重要性排序 → 预算约束下的逐级精度升级
- 预算充足时的快速路径已完成（全部走默认精度，不走优化流程，零开销）
- `AllocationResult` 输出结构已定义

  ```python
  @dataclass
  class AllocationResult:
      precision_map: Dict[int, Dict[int, torch.Tensor]]
      total_bytes: float
      budget_bytes: float
      avg_precision_bits: float
      compression_ratio: float
  ```

  输出样例（32 层、512 token、预算 50 MB 场景）：

  ```
  total_bytes:        42.3 MB     # 实际传输大小
  budget_bytes:       50.0 MB     # 网络预算
  avg_precision_bits: 8.4 bits    # 平均每个元素 8.4 比特（介于 FP8 和 INT4 之间）
  compression_ratio:  3.02x       # 相对 FP16 全量传输压缩了 3 倍
  precision_map:
    decode_0:
      layer_0:  tensor([16, 16, 16, ..., 8, 8, 8], dtype=int8)  # 前 100 个 token FP16，后 412 个 FP8
      layer_1:  tensor([8, 8, 8, ..., 8, 4, 4], dtype=int8)     # 前 230 个 FP8，后 282 个 INT4
      ...
      layer_31: tensor([4, 4, 4, ..., 4, 4, 4], dtype=int8)     # 全部 INT4
  ```

  可以看到，高重要性 layer 和高重要性 token 分到了高精度，低重要性部分自动降级。

##### 仍在进行中的工作
