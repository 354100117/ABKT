# ABKT 周报 — 2026.06.03

## 二、关键进展

### 2.1 ABKT 压缩功能修复

**问题**: ABKT 压缩逻辑始终不触发，即使在低带宽条件下也走 FP16 传输。

**根因**: `network_probe.py` 中的 budget 计算存在上限截断：
```python
# 修复前 — budget 被限制在 KV 大小以内，永远 >= fp16_total
budget = min(budget, total_bytes)

# 修复后 — budget 由带宽决定，allocator 自行处理 budget >= fp16 的情况
budget = bw * TARGET_TRANSFER_TIME  # 2.0s
```

**效果**: 修复后 ABKT 在低带宽场景下正确触发压缩。

### 2.2 两步协议 (Two-Step Protocol)

**问题**: KV 传输时间显示为 0s。原因是 `client.call()` 将 KV 传输和 decode 计算打包为一次 RPC，无法单独测量 KV 传输耗时。

**方案**: 引入两步协议：
1. Prefill 发送 KV cache → Decode 返回 ack（此时测量 KV 传输时间）
2. Prefill 发送 decode 参数 → Decode 执行推理并返回结果

**关键实现**:
- SocketServer 向 handler 注入 `_client_socket` 参数
- Decode handler 在两步模式下自行管理 socket 通信
- Prefill 使用 `send_with_progress()` + `recv_obj()` 精确计时

### 2.3 测试编排器 (Test Orchestrator) 重构

**原方案的问题**: tc 规则在 prefill_node.py 启动后、KV 传输开始时施加。但由于 Qwen2.5-3B 的 KV cache 仅 ~6 MB，全速传输只需 ~50ms，tc 来不及生效。

**新方案**: **pre-tc** — 在 prefill_node.py 启动前施加 tc 带宽限制，确保 bandwidth probe 测量到受限带宽，ABKT 做出正确的压缩决策。

```python
# 核心流程
tc_apply(prefill_host, pre_tc_mbps)        # Step 1: 施加 tc
verify_decode_node(decode_host, decode_port) # Step 2: 检查 decode
ssh(prefill_host, "python3 prefill_node.py ...")  # Step 3: 启动 prefill
# 监控 stdout，传输开始后可动态切换带宽
```

**场景定义** (基于 Qwen2.5-3B, KV ≈ 6.4 MB):

| 场景 | pre-tc | transfer-tc | 预期效果 |
|------|--------|-------------|----------|
| baseline | 无限制 | — | 对照组 |
| constant_low | 10 Mbps | — | 全程 ABKT 压缩 |
| constant_very_low | 2 Mbps | — | 极端压缩 |
| mid_drop | 100 Mbps | 2 Mbps | FP16→中途降级 |
| gradual | 50 Mbps | 10 Mbps | 渐进退化 |
| oscillating | 50 Mbps | 振荡 | 50→5 切换 |

### 2.4 ABKT DECISION 诊断行

在 prefill_node.py 中新增诊断输出，直观显示 ABKT 的决策依据：
```
[prefill] ABKT DECISION: COMPRESSED — budget=1.4MB < fp16=6.2MB (bw=0.7 MB/s, state=poor)
[prefill] ABKT DECISION: FP16 — budget=92.7MB >= fp16=6.4MB (bw=46.4 MB/s, state=degraded)
```

### 2.5 constant_low 场景测试结果

使用 173 tokens 的长 prompt，全程 10 Mbps 带宽限制：

| 指标 | 值 |
|------|-----|
| ABKT 决策 | COMPRESSED |
| 压缩比 | **3.1x** (avg 5.2 bits) |
| KV 大小 | 6.2 MB → **1.4 MB** |
| 精度分布 | FP8 × 26 层 |
| KV 传输时间 | 1.45s |
| 解码速度 | 11.5 tok/s (与 baseline 一致) |
| 生成质量 | 正常，无退化 |

**结论**: ABKT 在 10 Mbps 带宽下将 KV cache 压缩 3.1 倍，传输数据量从 6.2 MB 降至 1.4 MB，且不影响解码质量和速度。

## 四、待解决问题

### 4.1 mid_drop 场景效果不明显
- Qwen2.5-3B 的 KV cache 仅 6 MB，100 Mbps 下传输只需 ~0.5s
- tc 切换到 2 Mbps 时数据已写入 TCP 缓冲区，降速无法生效
- **可能方案**: 使用更长 prompt 增大 KV cache，或降低 pre-tc 带宽

### 4.2 send_time 计时异常
- 部分场景下 `total: 0.00s`，已加 debug print 定位中
- 可能与 SSH 管道缓冲或 socket 超时有关

### 4.3 Probe 带宽测量偏差
- 100 Mbps tc 下 probe 测到 ~8.3 MB/s (66 Mbps)
- 冷启动 probe 的数据量和测量方式可能不够精确
